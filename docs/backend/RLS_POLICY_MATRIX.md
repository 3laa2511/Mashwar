# Mashwar — Row-Level Security (RLS) & Authorization Policy Matrix
**Data Platform:** Supabase / PostgreSQL 15+  
**Architecture:** Least-Privilege Defense-in-Depth with Trusted Server-Side API  
**Status:** Reviewable Specification (Zero Active Database Credentials Exposed)  

---

## 1. Core Authorization Tenets & Safety Axioms

1. **Authentication is NOT Authorization:** A cryptographically valid Supabase Auth JWT proves identity, but never grants arbitrary access to records or operations.
2. **UI Role Switching is Cosmetic:** The demo `PopupMenuButton` in `flutter_mashwar/lib/` is for local interface evaluation only. The server ignores any client claim of role transition.
3. **Hiding a Button is NOT Access Control:** Disabling or hiding the "Accept Order" or "Delivered" button in the mobile app does not secure an endpoint. All mutation requests must be validated against the persisted state and authenticated actor permissions.
4. **Zero-Trust Identity Injection:** The server never uses `customer_id`, `captain_id`, `merchant_id`, or `fare` passed in request payloads. Ownership is extracted strictly from the verified JWT `sub` and database session state.
5. **No Service-Role Keys in Flutter:** The Supabase `service_role` key bypasses all RLS policies and is **strictly restricted to the trusted backend server environment**. It is never bundled, compiled into Dart, or exposed in any client environment.

## 3. Explicit List of Backend-Only Tables & Justifications

The following **14 tables** are strictly **Backend-Only** (no direct client reading or writing permitted via PostgREST/client SDKs):

1. `roles` & `permissions`: Internal authorization definitions.
2. `user_role_assignments`: Role escalation vector; managed strictly by server.
3. `pricing_rules`: Proprietary business formulas; prevents client price tampering.
4. `fare_quotes` & `fare_quote_line_items`: Authoritative quote generation and expiration.
5. `captain_subscription_payments`: Financial reconciliation for subscriptions.
6. `merchant_user_assignments`: Merchant branch authorization.
7. `payment_intents`: Gateway token generation and secret hashing.
8. `payment_transactions`: Gateway transaction logs and fee accounting.
9. `refunds`: Financial disbursement controls.
10. `webhook_events`: Gateway raw payloads and HMAC replay protection.
11. `audit_logs`: Immutable security and compliance trail.
12. `order_status_history`: Immutable append-only lifecycle log.
13. `captain_assignments`: Atomic race-condition dispatch management.
14. `cash_collections`: Financial cash-holding ledger.

## 4. PostgreSQL Row-Level Security Policy Definitions (Draft Implementation)

```sql
-- ============================================================================
-- 1. CUSTOMER ADDRESSES POLICIES
-- ============================================================================
CREATE POLICY customer_addresses_select_own ON customer_addresses
    FOR SELECT
    USING (auth.uid() = user_id);

CREATE POLICY customer_addresses_insert_own ON customer_addresses
    FOR INSERT
    WITH CHECK (auth.uid() = user_id);

CREATE POLICY customer_addresses_update_own ON customer_addresses
    FOR UPDATE
    USING (auth.uid() = user_id)
    WITH CHECK (auth.uid() = user_id);

CREATE POLICY customer_addresses_delete_own ON customer_addresses
    FOR DELETE
    USING (auth.uid() = user_id);

-- ============================================================================
-- 2. ORDERS POLICIES (READ ONLY VIA CLIENT; WRITES VIA SERVICE_ROLE)
-- ============================================================================
CREATE POLICY orders_select_participants ON orders
    FOR SELECT
    USING (
        -- Customer who created the order
        customer_id = auth.uid()
        -- Assigned captain
        OR id IN (
            SELECT order_id FROM captain_assignments
            WHERE captain_id IN (SELECT id FROM captains WHERE user_id = auth.uid())
            AND status = 'accepted'
        )
        -- Authorized merchant staff for the branch
        OR merchant_branch_id IN (
            SELECT branch_id FROM merchant_user_assignments
            WHERE user_id = auth.uid()
        )
        -- Operations agent or super admin
        OR EXISTS (
            SELECT 1 FROM user_role_assignments
            WHERE user_id = auth.uid()
            AND role_id IN ('operations_agent', 'super_admin')
        )
    );

-- Block direct client writes; all orders must be created & mutated via Trusted API
CREATE POLICY orders_deny_client_insert ON orders FOR INSERT WITH CHECK (FALSE);
CREATE POLICY orders_deny_client_update ON orders FOR UPDATE USING (FALSE);
CREATE POLICY orders_deny_client_delete ON orders FOR DELETE USING (FALSE);

-- ============================================================================
-- 3. CAPTAIN SUBSCRIPTIONS POLICIES
-- ============================================================================
CREATE POLICY captain_subscriptions_select_own ON captain_subscriptions
    FOR SELECT
    USING (
        captain_id IN (SELECT id FROM captains WHERE user_id = auth.uid())
        OR EXISTS (
            SELECT 1 FROM user_role_assignments
            WHERE user_id = auth.uid()
            AND role_id IN ('operations_agent', 'super_admin')
        )
    );

CREATE POLICY captain_subscriptions_deny_client_mutations ON captain_subscriptions
    FOR ALL USING (FALSE);
```

## 5. Storage Security & PII Protection Guidelines

1. **Private Storage Bucket (`captain-documents`):**
   - Public access is disabled (`public = false`).
   - Direct download URLs return `403 Access Denied`.
   - The trusted server issues presigned URLs with an expiration time of **900 seconds (15 minutes)** strictly to authorized operations agents during the document verification review process.
2. **PII Masking in Audit Logs:**
   - National ID numbers and phone numbers are stripped or hashed (`SHA-256`) before writing to `audit_logs`.
   - Never log authorization tokens, refresh tokens, SMS OTP codes, or gateway API keys.

## 7. Marketplace & Multi-Region RLS Addendum (2026-10-14)

The matrix below is required policy intent, not proof that policies are deployed or tested. Reconcile each row against actual tables before migrations.

| Data domain | Anonymous/public | Customer | Captain | Merchant owner/staff | Operations/admin |
|---|---|---|---|---|---|
| Active service areas | Read enabled public fields only | Same | Read areas they can opt into | Read areas where assigned branches operate | Manage/activate with permission + audit |
| Merchant public profile/catalog | Approved + active public fields only | Same | Minimum public merchant/order details when assigned | Own merchant/branches only | Review/manage with permission + audit |
| Merchant private records/docs | None | None | None | Own permitted records only, never review notes | Verification staff only, audited |
| Merchant orders | None | Own orders | Only orders offered/assigned as permitted | Own branch orders only | Operations permission, audited |
| Captain public profile | Minimal public DTO only | Minimal public DTO | Own public/private profile as appropriate | Minimum details needed for an order | Operations permission |
| Captain ID/license documents | None | None | Own submitted docs only where justified | None | Explicit verification permission, audited |
| Precise customer/captain location | None | Own saved location; order-related scope | Only assigned/eligible offer scope | Only relevant branch/order scope | Explicit operational permission, audited |
| Subscription & entitlements | Public plan details only | Own customer subscription if any | Own captain subscription | Own merchant subscription | Manage plan policy with audit |

Implementation requirements:
- Enable RLS and define explicit policies for every table containing personal, merchant, order, subscription, or location data; default-deny unknown roles.
- Do not use client-writable role claims or request-body IDs as authorization proof. Validate Supabase JWT and derive actor identity from verified claims.
- Ensure merchant membership checks include merchant and branch scope. Prevent cross-merchant reads/writes.
- Keep service-role credentials server-only. Any trusted API bypass of RLS must enforce authorization before querying/mutating.
- Test both positive and negative cases with real PostgreSQL/Supabase-like roles in an isolated environment; document tests as NOT RUN until executed.
